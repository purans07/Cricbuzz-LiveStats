# Phase 12 — Page 1: Home

Phase 12 builds Home, Live Matches, Top Players, Analytics, CRUD and Settings **one page at a time**, as requested in the adopted mentoring prompt. Home is implemented first. The remaining five pages are not yet registered or implemented; their roadmap cards are informational rather than links to empty screens. Phase 12 is still in progress.

## Purpose and design explained before implementation

Home orients the learner: explain the cricket project, identify the selected dataset, show saved record counts, provide usage instructions and make the project/folder/setup/SQL guides accessible. It must remain useful without a working database and must distinguish fictional sample data from saved provider data. Opening a dashboard is not evidence of a successful API refresh.

Use native Streamlit components and its built-in multipage navigation. The navy background, lighter panels and teal accent take their palette from the supplied Retail_Arcade.html reference, which remains untouched. This implements a Streamlit app rather than embedding or copying the reference's retail content. Avoid custom HTML for dataset values and avoid fragile CSS targeting private component internals.

There are no dataset-switch, database-path, key-entry, custom-SQL or mutation controls on Home. It reads the selected DATA_MODE/DATABASE_URL settings from the existing private configuration loader. Settings controls belong to their later page. Guide names map to fixed file paths, so a page visitor cannot use the documentation function to read an arbitrary file.

The rendered guide preview removes relative source-tree link destinations, since these paths are not web routes; the original downloadable guide preserves its links and text. HTTPS links and in-page anchors remain links. No public file server for the workspace is enabled.

## Backend logic and database calls

```text
main.py
  -> st.navigation (Home only)
  -> pages/01_Home.py
  -> ui.home.render_home()
  -> load_settings()
  -> Database(settings)
  -> OverviewService.read()
  -> one read transaction, two application SELECTs
  -> format and render
  -> dispose database resources in finally
```

`main.py` owns page configuration and the list of implemented routes. `pages/01_Home.py` delegates to a reusable presentation module. `ui/home.py` handles layout and user-facing states, not persistence. `services/overview.py` owns the consistent overview read. The existing central database manager opens an existing file in read-only mode, validates dataset mode/schema, enables query-only behavior and supplies the transaction boundary.

The two application SELECTs are:

1. Existing `dataset_status.sql`: mode and revision from the singleton dataset_state record.
2. The fixed overview SELECT: scalar COUNT subqueries over matches, v_active_players, teams and venues; MAX fetched_at among committed import_batches; count of committed batches whose completeness is partial/unknown.

These reads share the same transaction snapshot. The source schema's own connection-validation reads also run when opening a connection. No write transaction, initializer, migration, HTTP client or provider adapter is invoked. Active player counts exclude logically deleted profiles. Match counts include all stored statuses; they are not labeled ongoing or live-match counts. Teams and venues are reference-record counts. There is no live freshness calculation based on an import timestamp.

MAX fetched_at is the latest committed import across capabilities; it may be a player import rather than a match refresh. Failed and pending imports cannot advance it. Missing committed imports show a clear unavailable-time statement. Partial/unknown coverage remains visible. An import labeled complete describes that import's capability scope; it does not prove complete global cricket history.

## Reruns, caching and failures

Streamlit reruns the page after interactions. Home's small local overview is intentionally uncached, so it rereads after changes and does not show stale counts across mode/revision changes. It creates no shared live database connection or cached open transaction. Downloads use `on_click='ignore'` to avoid unnecessary reruns. When larger pages introduce caches, use explicit mode/filter/source/revision keys as specified in the architecture.

Configuration errors show a short setup message. Missing files, schema/mode mismatches and database errors show data unavailable while the static introduction and guides continue rendering. Counts are omitted on failure rather than replaced with misleading zeros. Exceptions and raw URLs are not shown or logged. Connections are disposed in a finally block even when reading fails. The page does not silently initialize, repair or overwrite a database.

Both local and public_readonly modes can view Home. This adds no administrative authentication or permission-changing interface; future CRUD controls must still rely on service access checks. Provider keys are never loaded by an API client or displayed by Home.

## Run locally

From the project folder, use:

```sh
.venv/bin/python -m streamlit run main.py --server.address 127.0.0.1
```

Then open [the local dashboard](http://127.0.0.1:8501). Existing private settings choose the database. To preview the saved sample without editing private settings:

```sh
DATA_MODE=sample DATABASE_URL=sqlite:///data/runtime/sample.db .venv/bin/python -m streamlit run main.py --server.address 127.0.0.1
```

The sample must already be initialized as described in the database guide. The Home page supports the preserved schema-1 sample and current schema-2 databases through the existing manager. A local preview was started in sample mode and inspected in the browser; the stored sample showed 72 matches, 12 active players, two teams and two venues. This is a local preview, not a public deployment.

## Verification and learning checkpoint

Ten focused checks cover active counts and unchanged read revisions, committed-import timestamps, actual Streamlit rendering/rerun, no HTTP on Home, changed counts after database edits, sample/live labels, missing database without accidental creation, redacted configuration failures, public-readonly viewing, allowlisted guide paths and safe guide previews. Related assertions are grouped in ten test functions. Tests use temporary databases and no API credentials. The full suite passes 389 tests; lint, formatting and whitespace checks pass.

The saved overview report records counts from the existing sample/live files using explicit test settings, with no private configuration values or credentials. These working databases were read only. Browser inspection confirms the theme, headings, sample label and four metrics render without an error.

Concepts learned: entry points versus page routes, native Streamlit components, rerun behavior, service/presentation separation, transaction-consistent reads, clear sample/provider provenance, graceful missing-data states and fixed-path documentation access.

Common mistakes to avoid: treating stored provider records as a fresh fetch, using a failed/pending import as freshness evidence, caching counts without revision keys, exposing connection URLs in errors, opening placeholders as working pages, and allowing arbitrary filesystem paths in a documentation viewer.

Home is complete. Next within Phase 12: explain and build Live Matches, including saved match/scorecard reads and deliberate provider-refresh behavior. No Phase 13 chart work has started.
