# Phase 12 — Page 5: CRUD

Home, Live Matches, Top Players, Analytics and CRUD are implemented. Settings is the final pending page in Phase 12.

## Purpose and concepts explained before implementation

CRUD provides forms for creating, inspecting, correcting and reversibly deleting player profiles and innings batting/bowling/fielding statistics. It uses the validated Phase 10 PlayerService and MatchStatsService rather than writing around their validation, ownership, relationship or transaction rules. This page does not create/delete whole matches, innings, participation records or career snapshots.

Separate catalogs, presentation and mutations. CrudCatalog owns fixed read-only selectors. The page owns forms, explicit confirmation and the loaded editing snapshot. Existing services remain authoritative for every write, including access checks, expected versions and source ownership. No API request occurs on this page.

## Components, inputs and outputs

| Component | Input | Output |
| --- | --- | --- |
| Sidebar route | CRUD | Fifth registered page |
| Dataset selector | Configured dataset, Saved sample, Saved provider | Existing target; access mode/timezone preserved |
| Record type | Players, batting, bowling, fielding | Current records including soft-deleted records |
| Record table | Read-only catalog | Stored fields, identity, ownership, deletion status and version |
| Action | Create, Edit, Delete, Restore, Release override | Appropriate form and confirmation controls |
| Existing-record selector | Stable selected identity | Loaded snapshot and expected version |
| Reload selected record | Explicit button | Replace the loaded snapshot with current committed values |
| Profile form | Name, optional role and styles | Service-validated profile creation/update |
| Statistic relationship selector | Known match/innings/participant combination | Correct fixed identity/team fields for creation |
| Statistic fields | Whole-number text or blank; dismissal text | Known values or NULL, never implicit zero |
| API override | Explicit checkbox when ownership is api | Allow a local correction/deletion/restore under service policy |
| Delete/release confirmation | Explicit checkbox | Apply only when confirmed |
| Apply button | Form submission | Commit or safe validation/conflict message; reload after success |

Read-only visitors can inspect tables but no administrative forms are rendered. Service checks also prevent writes if a caller bypasses the UI. This is local-operator administration, not a new public login/authentication system. A local deployment must remain within its intended trusted access scope.

Dataset choice is session-only and never rewrites .env. Configured dataset preserves a custom validated path; the other choices use the project's existing sample/live files. Missing targets produce a message without initialization or repair. The page does not automatically migrate schema versions.

## Database reads, relationships and mutation calls

CrudCatalog reads all profiles, including deleted ones; the role catalog; or one fixed statistics table joined to player names. Statistics table names come only from the service's fixed kind allowlist. No user-supplied SQL identifier is interpolated.

Creation choices join existing innings, matches, match_players and active players. Batting requires the innings batting team; bowling and fielding require the innings bowling team, matching the existing service relationship rule. The selected relationship supplies match_id, innings_id, player_id and team_id to create; visitors do not type potentially inconsistent IDs. Existing rows are not excluded from the creation selector: attempting to create an already-existing innings/player record produces the service's conflict message. Restore is the appropriate way to recover a soft-deleted row with that identity.

Creating a new profile does not create match participation. A profile with no imported/recorded participation therefore cannot immediately receive arbitrary match statistics from this form. Match/innings/participation management is outside the page's current scope.

```text
select target/entity/action/identity
  -> read catalogs
  -> retain loaded snapshot in session state
  -> render fields with identity/version-specific keys
  -> Apply
  -> PlayerService or MatchStatsService
  -> validate values, ownership, relationship, access and expected version
  -> one write transaction
  -> atomic change and revision bump only when data changes
  -> commit completes
  -> clear loaded snapshot and advance form generation
  -> rerun and display current committed records
```

The UI never edits protected identity/source/batch/version/ownership columns directly. API override and release use service operations rather than editable ownership text. Services parameterize values, enforce foreign keys and roll back conflicts. Blank statistics become None; typed zero remains zero. Legal balls are explicitly labeled as legal balls, not decimal cricket overs. Numeric text must contain ASCII nonnegative whole-number digits; bounds and relationships are rechecked by the service/database. Invalid flags, batting positions, wickets, boundary totals and maiden counts remain subject to existing validation.

## Expected versions and rerun safety

The first load stores a copy of the selected existing record and its version in session state, keyed by target path/entity/action/identity and form generation. Submission reruns do **not** replace that version with a newer database read. The service can therefore reject a stale edit rather than overwriting a concurrent change. A conflict asks the operator to reload and review, not automatically retry.

Fields use identity/version-specific widget keys so switching records, datasets or reloading a changed version cannot carry unrelated edits into the next record. After a successful write, a new form generation clears creation fields and the loaded snapshot. This prevents the old submitted name/statistics from remaining as a prefilled second creation. The success message is shown after the service transaction returns and a rerun rereads current data. It does not claim success on validation or commit failure. No cached result table is introduced.

## Deletion, restore and provider ownership

Delete is a logical is_deleted change, never a physical purge. It requires a confirmation checkbox. Deleting a profile hides its dependent performances and career rows through active views without deleting the underlying relationships or statistics. Restoring the profile makes its otherwise-active dependents visible again; dependents separately soft-deleted remain deleted.

API-owned mutations require an explicit override checkbox. A successful mutation changes ownership to override under the existing lifecycle policy, preserving local corrections against later imports. Manual records remain manual. Restore follows the same API-ownership checks. Editing a deleted record is rejected until it is restored.

Release override requires confirmation, applies only to a valid active override and returns control to api ownership. It does not fetch or instantly revert values; a later successful API import may replace them. Deleted overrides must first be restored before release, as enforced by the service. Attempting an action inconsistent with the current record produces a useful policy message.

The UI also exposes Restore/Release as selectable actions on records where they may not apply; authoritative service checks explain why rather than guessing a policy in the page. A no-op valid service call may leave revision unchanged.

## Failure handling and practical limits

Value errors from the validated services are shown as actionable messages; raw database exceptions/URLs are not exposed. Stale versions get a specific reload/review message. Database/access failures show that the change could not be committed. Central transactions ensure invalid writes do not leave partial updates.

Tables/catalogs are uncached and currently read complete small datasets; large deployments need pagination and scoped relationship selectors after profiling. The page does not add bulk editing, permanent deletion, audit-history browsing or public administrative authentication. Restorable deletion and last-batch/ownership fields are not a complete immutable audit log.

No actual working-data edits were needed during implementation. All create/edit/delete/restore/release checks run against temporary per-test database copies. Browser preview is for inspection only; no form should be submitted there merely to demonstrate testing.
